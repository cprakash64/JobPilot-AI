# People Who Can Help — living implementation plan

Status: implementation validated in the primary Jobs workflow (2026-07-26)

## Existing architecture discovered

JobPilot is a compact monorepo. `apps/api` is FastAPI with synchronous SQLAlchemy sessions,
Alembic migrations (current head `0019_education_gpa_scale`), JWT bearer authentication, Pydantic
settings, a Redis-backed Celery worker, database audit events, and safe error envelopes.
`apps/web` is Next.js 16/React 19 with a typed fetch wrapper, Tailwind design tokens, Vitest, and a
minimal `/jobs/[id]` page. PostgreSQL and Redis run through Compose. No reusable feature-flag or
metrics library exists, so this feature uses typed settings, a deterministic rollout policy, safe
structured logs, database run/cost records, and documented metric names.

Validation commands: `make test-api`, `make test-web`, `make test-extension`,
`docker compose config`, `cd apps/api && alembic upgrade head`, `alembic downgrade -1`,
`python evaluation/people_recommendations/evaluate.py`.

## Proposed architecture and data flow

1. The authenticated job page reads `GET /jobs/{id}/people`.
2. A config-native rollout policy gates recommendations, email, outreach, network matching, and
   PDL independently.
3. Discovery builds a deterministic typed `JobPeopleSearchProfile` from normalized job/company
   fields. It validates domains and expands related titles; no person is generated by an LLM.
4. A provider-neutral orchestrator searches recruiter, manager, and referrer categories
   independently. Apollo is primary, PDL is an optional fallback, and a deterministic mock is
   available only when explicitly configured.
5. Preliminary ranking limits enrichment. Normalization, conservative entity resolution, and
   category-specific versioned scoring produce candidates. Confidence is separately calibrated
   from evidence quality, freshness, corroboration, missing fields, and conflicts.
6. Canonical people and field-level provenance are shared; job candidates and user
   personalization are separate. Fresh database results are reused. A Redis lock coalesces
   concurrent runs; the database run record is the durable idempotency/cost ledger.
7. Email lookup is explicit and budgeted. Hunter/Apollo results must be professional-domain
   addresses and verified before being displayed as verified. Ciphertext and a keyed hash are
   stored; plaintext never enters logs or analytics.
8. Outreach is generated on demand from a grounded template using only the job, user profile, and
   structured evidence. The UI requires manual review and never sends.

## Database changes

Migration `0020_people_who_can_help` adds canonical people, provider identities/provenance, job
candidates, user recommendations, discovery runs, and feedback. Foreign keys and unique
constraints isolate user state and make discovery/email operations idempotent. Account deletion
cascades user recommendations, runs, and feedback. Canonical provider-derived records expire via
configured retention and are not exported as private user data.

## API contracts

- `POST /jobs/{job_id}/people/discover`
- `GET /jobs/{job_id}/people`
- `POST /jobs/{job_id}/people/{recommendation_id}/email`
- `POST /jobs/{job_id}/people/{recommendation_id}/outreach-draft`
- `POST /jobs/{job_id}/people/{recommendation_id}/feedback`
- `POST|DELETE /jobs/{job_id}/people/{recommendation_id}/save`
- `POST /jobs/{job_id}/people/{recommendation_id}/contacted`

Responses expose structured reasons, limitations, freshness, safe profile URLs, and confidence
labels; they never expose provider IDs, raw payloads, or secrets.

## Provider, ranking, security, and privacy decisions

Provider adapters have bounded timeouts, response-size limits, strict normalization, safe errors,
and no LinkedIn scraping. URLs are HTTPS-only and host-validated without server-side fetching.
Scoring weights live in `app/people/scoring.py` under version `people-v1`. Weak results are
suppressed rather than used to fill categories. Email protection derives a dedicated Fernet and
HMAC key from `PEOPLE_DATA_ENCRYPTION_KEY` (required in production when email is enabled).
Rollout defaults to disabled. Rate limits, daily global/per-user budgets, per-job caps, cache TTL,
audit events, suppression after incorrect reports, and Redis request coalescing limit harm/cost.

## Testing and evaluation strategy

Unit tests cover extraction, title expansion, domains, normalization, scoring/confidence,
explanations, deduplication, email policy, flags, budgets, cache fingerprints, and grounded
drafting. API integration tests use only synthetic mock-provider data and cover disabled,
discovery, cache, authorization, email, save/contact, feedback, and deletion. Frontend tests cover
states, categories, safe links, actions, limitations, and accessibility semantics.

`evaluation/people_recommendations` contains a versioned redacted benchmark, labeling guide, and
runner that writes JSON and Markdown reports and fails unmet release thresholds unless
`--allow-incomplete` or `PEOPLE_EVAL_ALLOW_INCOMPLETE=true` is explicitly used.

## Rollout and rollback

Deploy schema first with all controls disabled. Enable internal users, then beta identities, then
a deterministic percentage, watching documented metrics and feedback before `all`. Keep email,
network matching, PDL, and outreach off until separately approved. Roll back by disabling flags;
then deploy the prior application. Downgrade `0020` only after retention/export review because it
deletes feature data.

## Live Apollo provider repair (2026-07-26)

The live internal rollout reached discovery but the Apollo adapter called the obsolete
`/api/v1/mixed_people/search` path with the obsolete singular
`q_organization_domains` field. It collapsed 401 and 403 into `provider_auth`, used reason names
outside the frontend contract, and expected full enrichment fields from People API Search even
though current search results contain an obfuscated last name and require a separate enrichment
call. Its enrichment adapter also used `GET /people/match`; Apollo documents `POST` and recommends
`POST /people/bulk_match` with a `details` array for IDs returned by search.

The adapter now uses `POST /api/v1/mixed_people/api_search`, `x-api-key`, JSON list filters,
one-based `page`, and bounded `per_page`. Search-result normalization accepts the documented
partial schema, and selected IDs are enriched in one bounded bulk request with personal email and
phone reveal disabled. Authentication, authorization, rate limit, timeout, network, schema,
circuit-open, and generic availability reasons remain distinct through persistence and the UI.
Failure logs contain only reason, provider, HTTP status, duration, and discovery run ID.

The in-process circuit remains enabled at three failures with a 60-second reset. An expired
circuit now performs a clean half-open attempt instead of immediately reopening from the old
failure count. In local development, recreating the API process safely clears its in-memory
circuit; it must not be disabled.

The frontend already had a user/job-keyed shared promise that coalesces concurrent discovery
requests. An explicit per-controller synchronous in-flight guard now closes the remaining
same-click window before React commits disabled state. Tests cover rapid repeated activation and
prove it creates exactly one discovery POST.

Runtime cleanup preserves provider keys byte-for-byte. The encryption placeholder is replaced
only on an exact literal match with a 32-byte URL-safe base64 key; internal rollout contains one
local login, beta IDs are empty, and email discovery, network matching, and PDL fallback are off.
